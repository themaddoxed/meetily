## Historical FEAT-087 opt-in census on the prior source snapshot

The app contains one product analytics SDK, `posthog-rs` 0.3.7. The frontend preference and initialization boundary is in `frontend/src/components/AnalyticsProvider.tsx`:

- A missing `analyticsDefaultOffMigrationV1` marker forces `analyticsOptedIn` to `false`, writes the marker, and saves the store. This also overrides an old `analyticsOptedIn: true` preference.
- With the marker present, only the boolean value `true` enters initialization. Missing, false, string, number, and null values stay opted out.
- The current settings switch is the only affirmative path that persists a new opt-in and calls analytics initialization. Event methods in `frontend/src/lib/analytics.ts` also check that the frontend analytics wrapper was initialized.

On the native side, `frontend/src-tauri/src/analytics/commands.rs::init_analytics` creates the PostHog client with analytics enabled. `AnalyticsClient::new` creates the SDK client only when its config is enabled and the key is non-empty. The global client starts empty; event commands do not create it. Current frontend call sites gate initialization through the provider or the explicit consent switch. The native command itself trusts its caller, so any future frontend call to `init_analytics` must remain behind the consent path.

The analytics store also contains identifiers and aggregate usage state such as `user_id`, session fields, first-launch state, daily-use date, platform/OS/architecture, and feature-use counters. The provider reads or writes those values only after affirmative initialization; tests below verify the no-consent startup path does not call any analytics method.

Model and provider traffic is separate in code. Whisper, Parakeet, and summary model downloads use `ResumableDownloader` in `frontend/src-tauri/src/model_download.rs` through their model-specific managers. OpenAI, OpenRouter, Ollama, Groq, and Anthropic provider calls use their own request modules. The inspected source and dependencies contain no Xray or other corporate telemetry SDK/import/config. A source search found no Tauri updater plugin, updater SDK, or app-update endpoint in the current frontend and Tauri source. This is a source-level separation check, not a packet capture of live application traffic.

## Historical FEAT-088 opt-out behavior fix on the prior source snapshot

Before this change, confirming opt-out invoked `track_analytics_disabled` while the PostHog client was still active. Opening the transparency modal also invoked a tracking event. Both events were unnecessary for withdrawing consent; the first could send analytics as part of the opt-out action.

The opt-out UI now saves the false preference and disables the analytics client without sending a tracking event. The transparency-view and analytics-disabled event methods and Tauri commands were removed, along with their command registrations and browser mock entries. Explicit opt-in and its existing events remain available after the user enables analytics.

The new Node behavior test executes the actual provider and consent-switch components with mocked stores, React hooks, analytics methods, and Tauri invokes. It checks first launch, old opt-in without the migration marker, saved opt-out, malformed preference values, explicit current opt-in, and opening/confirming opt-out. No real SDK client or network connection is used.
