# Передача Codex: надёжный, открытый и приватный macOS-рекордер

Дата: 22 сентября 2026 года.

## Начать здесь

Цель владельца — самостоятельное понятное macOS-приложение для встреч: надёжно сохранять разговор, локально расшифровывать и получать полезный результат, не требовать аккаунта или оплаты за функции и не отправлять данные скрытно. Источники идей — Meetily - Actually Free и Amanu. Цель не состоит в объединении трёх кодовых баз или переносе всех возможностей доноров.

Полное исходное [архитектурное ревью](architecture-review-2026-09-22.md) сохранено без изменения содержимого, включая карту всех 57 исходных задач. Этот handoff уточняет приоритеты и рекомендации того ревью. Это не новый tracker и не выполненная реализация. Канонические статусы и зависимости остаются в существующих `docs/prd`; новые рабочие списки рядом с ними не создавать.

Публикацией добавлены только два документа. Продуктовый код, существующие PRD, AGENTS.md, настройки GitHub, видимость репозитория и требования выпуска не изменены. Фраза «репозиторий не изменён» в исходном ревью описывает момент его подготовки, до этой публикации. Пожелание открытого продукта не является разрешением сделать приватный репозиторий публичным.

## Что уточнено после повторной проверки

### 1. Сохранность результата — важнее нового общего job engine

Повторно подтверждено по коду: cancellation registry summary индексируется `meeting_id`, cleanup удаляет запись без сравнения владельца, тогда как база уже использует `lifecycle_run_id`. Публикация `summary.md` и suggested title идёт до проверки run ownership в `update_process_completed_for_run`. Эти узкие проблемы остаются актуальны; сначала исправлять их, а не внедрять универсальную очередь всех стадий. [C1, C2; F4/F5 исходного ревью]

Наблюдение о race является статическим выводом о допустимом чередовании, а не результатом запущенного воспроизведения. В частности, B может сменить owner после проверки A и закончить сохранение раньше отката A. Для реализации сначала закрепить конкретное чередование управляемым тестом. Отрицательный результат исследования должен быть допустим: ревью не является приказом создать дефект, которого нет на новой базе.

### 2. Не переносить из Amanu принцип «папка — вся база»

В предыдущем `amanu-analysis.md` есть противоречие: в пояснении Rust/SQLite названы владельцами рабочего состояния, а строка таблицы предлагает SQLite как индекс. Исследование также привязано к preservation main, а не текущему product tip. Поэтому его архитектурные рекомендации нельзя применять как готовый план к сегодняшнему коду. [A3]

Предлагаемая граница для нашего приложения:

- исходный звук и checkpoints принадлежат файловому хранилищу; база не заменяет аудиобайты;
- редактируемые метаданные встречи, принятые транскрипты/итоги, версии и владельцы processing runs — канонические данные SQLite;
- `summary.md`, читаемый transcript, manifest экспорта и поисковый индекс — версионированные производные; их можно восстановить из канонических данных и исходных файлов;
- переносимый пакет встречи — полезная возможность экспорта/восстановления, но не вторая независимо редактируемая библиотека;
- импорт внешних изменений — явная операция с проверкой версии/конфликта, а не скрытая двусторонняя синхронизация папки и базы.

Это предлагаемое целевое разделение, не заявление о том, что код уже полностью ему соответствует. Не переносить все данные за один шаг: сначала ограничиться сохранением summary и сохранить совместимость существующих форматов.

### 3. Не делать новые рекомендации скрытыми блокерами

R5 из исходного ревью — исследование возможного неограниченного ожидания, не доказанный новый дефект на каждом запуске. Выполнять адресно; не начинать выделение capture в другой процесс без воспроизведения.

R6 — запись без готовой STT-модели — полезное расширение поведения, а не автоматически обязательное исправление прежней спецификации. Делать отдельной следующей карточкой; не менять `auto_save=false` скрытно.

R7 — сохраняемый признак неполноты записи — привязать к существующему FEAT-071, а не создавать второй проект управления источниками. Не смешивать это с diarization.

R2 — удобный scoped entrypoint — небольшое улучшение процесса. Пока его нет, разрешённые явные целевые команды из карточки достаточны: не блокировать каждый продуктовый fix завершением проекта по toolchain. Полный gate не ослаблять.

### 4. «Локальное» не равно «всё всегда приватно»

Amanu явно документирует аналитику, включённую по умолчанию, и сетевые/CLI-провайдеры. README описывает автоматический переход к следующему настроенному backend при исчерпании подписки. Это не те defaults, которые нужно наследовать. ActuallyFree документирует отсутствие analytics transmission, но даже это не является доказательством отсутствия любых сетевых запросов нашего форка. [A1, A2, B1]

В текущем summary-коде есть логирование извлечённого названия встречи. Поэтому проверка приватности должна охватывать не только telemetry client, но и содержимое обычных диагностических логов. Это наблюдение о конкретном log call, не утверждение об утечке в облако. [C2]

Перед переносом конкретной возможности: закрепить donor SHA и точные файлы; проверить лицензию этих материалов и требуемых зависимостей; выбрать `reuse-existing`, `adapt-small-piece`, `implement-contract` или `defer`; связать решение с существующим task ID и одной приёмкой. Сохранить attribution при переносе кода. Не запускать общий анализ обоих репозиториев в каждой сессии и не обновлять donor SHA автоматически при очередном релизе. Более новый HEAD не отменяет прежний pinned intake и не разрешает общий merge.

## Проверяемый контракт приватности

Это предлагаемые критерии FEAT-082 и минимального FEAT-080, а не уже подтверждённые свойства текущей сборки.

1. После явной установки необходимых моделей локальные record/transcribe/diarize/summary выполняются без передачи содержимого встречи наружу. Отсутствие локальной модели не выбирает облако автоматически.
2. Provider, endpoint и отправляемые данные видны до сетевой обработки. Любой fallback через границу local → remote требует отдельного включения; установленный CLI не означает локальную обработку.
3. Продуктовая аналитика не создаётся и не отправляется. Старый preference не включает её скрытно. Логи не содержат transcript, summary, ключи или названия встреч; поддержка получает диагностический пакет только по явному действию с предварительным просмотром/очисткой.
4. Загрузки моделей и обновления — отдельные сетевые действия без содержимого встреч. Внутрисетевой сервер — тоже другой компьютер, а не обработка на устройстве. Не путать отсутствие analytics с отсутствием сетевого трафика.
5. Запись, requested/actual sources, пауза и деградация видны. Если mute не удаляет звук из raw, интерфейс не обещает обратного. Не использовать значок выключенного микрофона как ложное обещание, что звук нигде не сохраняется.
6. Автозапись выключена до явного выбора. Отказ в календаре не блокирует ручную запись. Автостоп не завершает чужую ручную сессию.
7. Сохранённый исходник не удаляется при ошибке обработки. Удаление и сроки хранения явны; экспорт и recovery не должны обходить выбранное пользователем ограничение хранения. Локальный файл сам по себе не означает шифрование диска или защиту от резервного копирования ОС — таких гарантий не заявлять без отдельной реализации и проверки.

Начальная проверка — адресные тесты границ вызова provider/analytics и очистки логов. Проверка packaged local-only поведения — отдельный native-сценарий; browser interception не доказывает отсутствие Rust/sidecar egress. Не строить ради этой задачи общий сетевой firewall приложения.

## Ближайшие шесть единиц работы

Подробно актуализировать только эту пачку. Остальные 103 дочерних шага сохранить с их IDs как предварительную очередь, а не переписывать все заново. Метки ниже — ссылки на предложения, не новые mdtask IDs. Сначала использовать существующий ID; новый нужен только для подтверждённого дефекта или отдельно принятого расширения.

### 1. R1 — Один понятный вход в работу

**Результат:** агент знает product base, источник PRD, разрешённую область и одну следующую ready-задачу.

**Стартовые материалы:** два PRD, execution-plan, действующий AGENTS.md выбранного checkout и Git policy.

**Готово:** короткая актуальная запись заменяет неоднозначные инструкции; расхождение зависимости FORK-122/FEAT-086 согласовано по выбранной семантике и отражено во всех оставшихся представлениях; существующий валидатор не видит неизвестных ID/циклов.

**Не входит:** merge веток, перенос всех документов в main, migration Beads, новый tracker и автоматизация графа. Недоступность необязательного overlay не блокирует чтение доступного mdtask backlog.

### 2. R2 — Адресная проверка вместо ложного quick

**Результат:** одна область проверяется без автоматического запуска остальных областей и упаковки.

**Стартовые файлы:** `scripts/check.sh`, `frontend/package.json`, связанный тест маршрутизации и существующая инструкция проверок.

**Готово:** docs-route не запускает browser/Rust/build; выбранный audio/summary route выполняет указанный фильтр/модуль; неизвестный scope отвергается; `--full` сохраняет прежний состав. Если тестовый фильтр найден неверно и выполнено ноль целевых тестов, это не PASS. Названия и наличие команд проверить, а не выдумывать.

**Не входит:** новый change-impact engine, новая CI-платформа, DMG, подпись и review всех старых линтерных предупреждений. Пока маршрут не готов, явно заданные узкие команды допустимы.

### 3. R3 — Одна попытка summary владеет своими действиями

**Результат:** старая попытка не снимает отмену/статус новой и ранняя ошибка не оставляет неработающий процесс.

**Стартовые файлы:** `summary/commands.rs`, `summary/service.rs`, `database/repositories/summary.rs`, при необходимости `meeting.rs` под `frontend/src-tauri/src`.

**Готово:** A не удаляет token B; cancel относится к выбранному run; все ранние выходы освобождают собственный token; ошибка записи chunks не оставляет PENDING без worker. Политика duplicate start явна и протестирована.

**Проверка:** fake provider и управляемые barriers; без платного API, модели и native capture.

**Не входит:** pipeline scheduler, новое семейство job IDs, смена шаблонов или downloader.

### 4. R4a — Старый результат не перезаписывает новый

**Результат:** принятие generated summary и её suggested title проверяет владельца; устаревшая попытка не может опубликовать или откатить результат новой.

**Стартовые файлы:** `summary/service.rs`, `summary/persistence.rs`, repositories summary/meeting и профильные тесты.

**Готово:** управляемый A/B regression покрывает устаревшую публикацию и rollback; принятие данных и lifecycle согласовано транзакцией/существующим узким механизмом; stale-run не делает файловых изменений после результата B.

**Не входит:** перенос всей базы и автоматический экспорт всех типов. Допустима небольшая общая подготовка для R4b, но не новая универсальная transaction framework.

### 5. R4b — Ручная правка и файл сходятся после сбоя

**Результат:** пользователь видит и экспортирует последнюю принятую версию, а сбой публикации не теряет текст.

**Зависимость:** R4a и выбранный узкий контракт версии результата.

**Готово:** manual save и generation используют согласованный путь; поздняя generation не затирает более новую ручную правку; file-write error/crash/reopen оставляет канонический текст и либо актуальную файловую копию, либо явный pending export с безопасным повтором. При изменении схемы есть тест обновления заполненной временной базы.

**Не входит:** двусторонняя синхронизация папок, сторонние экспортеры, redesign редактора и смена BlockNote.

### 6. FORK-051 + FEAT-071 — Доказать текущую запись на одном артефакте

**Использовать:** существующие FORK-119–122 и FEAT-083–086, не новые копии этих задач.

**Результат:** известны реальные mic/system tracks, их временные позиции, поведение pause/resume, stop/Quit/reopen и оставшиеся физические ограничения.

**Готово для проверенного сценария:** один source/package идентификатор; разнесённые сигналы с тишиной до/после паузы; измерение позиций по заранее выбранному допуску; source-control семантика соответствует raw/downstream; отсутствие system frames не выдаётся за полноценную запись двух источников. Разрешения и device switch имеют собственные результаты, а не наследуют общий PASS.

**Не входит:** автоматический TCC reset, скрытые изменения пользовательских разрешений, миграция профиля, новый DSP и повторная сборка после каждого тестового комментария. Неизменившийся артефакт можно использовать для нескольких критериев. После изменения capture повторяются затронутые сценарии на новом артефакте, а не предъявляется старый smoke как новый.

**При провале:** сохранить минимальный пример и назвать конкретный дефект; исправлять только его в согласованной области. При недоступном Mac/разрешении отметить этот шаг BLOCKED и выполнять ready summary-карточку, а не ждать или создавать бесконечные диагностические пакеты.

Порядок 3–6 не является искусственной dependency-цепочкой: native-сценарий можно выполнить раньше, если доступен нужный артефакт и среда. Одновременно писать общие recording/storage-файлы нескольким агентам нельзя.

## Следующие пачки, а не новые обязательные эпики

После первой пачки: минимальные privacy/first-run критерии FEAT-082/080, сохраняемая полнота источников внутри FEAT-071 и явно принятый capture-without-STT. Затем одна сквозная внутренняя сборка: запись → stop → reopen → локальная обработка → итоги → существующий экспорт. Полезный результат проверяется также через несколько checkpoint и длительную встречу; найденные проблемы превращаются в узкие regressions, а не общий performance rewrite.

После устойчивого ядра — поиск и полный TXT/Markdown/JSON, вопрос по одной встрече, компактные системные команды. Diarization, people, PDF/DOCX и автозапись добавляются отдельными полезными порциями. Глобальный search не обязан блокировать первый ответ по явно выбранной встрече; отсутствие speakers не должно блокировать полный текстовый экспорт. Уточнения этих рёбер применяются только вместе с соответствующим изменением карточек.

Имя, bundle-ID upgrade, подписанный updater, доставка и полный FORK-053 остаются отдельными этапами. Intel/arm64, macOS 14.2 и все действующие требования публичного выпуска сохранены. Ранняя внутренняя сборка не называется готовым публичным Alpha.

## Как Codex проверяет независимо и не зацикливается

Независимость — это проверка утверждения по коду, а не ещё одно согласие с текстом отчёта. Для выбранной карточки проверить только относящееся к ней finding: действительно ли есть путь вызова, кто владеет состоянием, какой observable regression его отличает. Результат проверки: `confirmed`, `already-fixed`, `not-reproduced` или `needs-input` с коротким основанием. Не превращать весь документ в новый обязательный аудит каждой сессии.

Один исполнитель на продуктовую область. Для конкурентности, сохранности данных, permissions и release — один ограниченный независимый reviewer, когда доступен и разрешён. Он получает карточку, конкретный diff, interfaces и фактические результаты тестов. Если отдельный reviewer не запускался, прямо написать это; самопроверка не переименовывается в независимое ревью.

Обычная единица работы: минимальный код, адресный тест, необходимая небольшая документация и приёмка. Не делать самостоятельные задачи «ещё раз проверить план», «проверить review» и «перехешировать отчёт», если нет конкретного нового риска. Внешний native-sign-off и публичный release gate остаются отдельными, когда требуют иной среды.

Ограничитель петли: после двух безрезультатных циклов по одной причине прекратить автономное исправление, сохранить исходный fail и сформулировать узкий blocker. Это не разрешение закрыть дефект. Повтор полного gate без изменения соответствующих входов или новой гипотезы не даёт нового доказательства. Один адресный повтор допустим для классификации flaky-теста; первый fail не скрывать.

Два режима завершения: `DONE` по проверенному результату либо `BLOCKED` с конкретным отсутствующим входом. Новая идея вне scope попадает в существующий backlog/intake после проверки на дубликат, но не начинает исполняться автоматически. Существенное изменение согласованного контракта требует отдельного решения; безопасная независимая работа при этом может продолжаться.

Не устанавливать жёсткий общий лимит строк/файлов или выдуманный token budget. Ограничивать один пользовательский результат, поверхность изменения и число неуспешных повторов. Крупный review сам по себе не является причиной распилить уже согласованную минимальную транзакцию на небезопасные части.
