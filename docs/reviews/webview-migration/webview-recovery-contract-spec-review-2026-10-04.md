## Source-backed decisions to freeze

1. **Legacy compatibility and startup table — candidate lines 32–40, 109–112.** Existing `migration.rs:683–738` accepts valid completed file journals and refuses incomplete ones. Its journal schema at lines 60–67 has no root bindings, web hash or receipt. Preserve that distinction explicitly: valid legacy Completed without combined intent follows existing normal/first-launch behavior; legacy incomplete without a bound combined intent stays safely blocked and must not be automatically promoted into a combined migration using newly supplied roots. New pending intent without journal, with Preparing, or with file Completed remains recovery-required. A matching durable combined receipt makes that intent terminal; it must not stay “pending” merely because the retained intent file exists. Corrupt/conflicting intent or receipt fails closed. Do not reinterpret old Completed as proof of WebView import, or require a nonexistent new receipt for every historical file-only migration.

2. **Preparing needs a real resume policy — candidate lines 58–61.** `migration_commands.rs:139–142` rejects Preparing; `migration.rs:765–766` requires empty staging. The copy primitive at lines 960 onward creates randomized `.copy.tmp` files, so hard termination can leave both verified final staged files and partial temporary files. Simply retrying stage_manifest cannot resume. Reuse existing validation/copy helpers through one owned resumable seam: verify completed staged paths against manifest, copy only missing entries with create-new semantics, and define durable ownership for per-file temporary work. Preserve incomplete temporary bytes without including them in publication; any new staging generation/quarantine must remain same-owner, bounded by rechecked disk budget and durable pointers. Unknown files/symlinks/conflicting hashes stop safely. Decide exactly which crash states are resumable and which present a blocked recovery diagnostic; do not label safe refusal successful recovery. Keep legacy incomplete operations outside this new automatic protocol unless their roots are separately and explicitly admitted.

3. **Combined marker/preferences/receipt protocol — candidate lines 62–82.** The current sink (`webMigration.ts:246–275`) writes preferences before IDB and only best-effort rolls back errors; import short-circuits on an existing marker (`:413`). `indexedDBService.ts:754–776` confirms marker identity, uses add for records and returns already_imported without re-reading record contents. The proposed reversed order therefore needs a new versioned marker, not a semantic reinterpretation of every existing marker. Freeze states such as records_committed/preferences_pending and preferences_applied; store the exact allowlisted preference intent with the records. A safe initial collision policy is absent-or-equal target preference values only; reject differences before any write unless an explicit reviewed overwrite consent policy is chosen. Absent package keys remain untouched. Store/check collision expectations before committing and replay only the same pending intent. Never replay old preferences after a durable terminal receipt; later user edits are legitimate.

   Browser readback should enumerate intended records and recompute their canonical content hashes/counts, read each intended preference, and validate full marker identity/version/state against the retained package. Report a typed result from the admitted recovery window; Rust binds it to the active operation/package/manifest/root identities, independently re-verifies files while pending, then durably writes the matching receipt (including directory sync) before declaring completion. A mere payload-hash echo is not a data readback. Rust still trusts the adapter's browser facts: no boolean, nonce or hash makes them independent native inspection of IndexedDB. Document that trusted-adapter boundary and reject unbound requests/senders. If receipt durability succeeded but its response was lost, startup recognizes the receipt without restoring old preferences. A legacy browser marker alone cannot be silently upgraded to combined completion or justify overwriting later preferences; define its explicit compatibility outcome.

4. **Identity pair is a real remaining admission, not solved by fixtures — candidate lines 83–88.** Current config identifier is `com.meetily.ai` (`tauri.conf.json:5`). The adapter only enforces nonempty different source/target strings, and current commands derive app-data but accept requested identity strings. Export must bind source identity to its actual running producer; import must bind target to actual configuration and enforce an explicitly admitted source-target pair. A free-text user identity is not that admission. Final branding remains parked: do not invent a different production target or reopen naming merely for this review. The coordinator can be designed with explicit admitted-pair data and tested with fixtures, but an enabled production transfer between actual applications remains blocked until the pair and compatible exporting producer exist. Installed old-to-new proof remains FORK-124/125/160.

5. **User export entry can be resolved from current source — candidate lines 101–104.** `settings/page.tsx:117` already mounts PreferenceSettings. Add a separate export control within `PreferenceSettings.tsx:187–247` Data Storage Locations, retaining the recordings folder action. Database/models blocks there are commented out, not active controls. Add only `frontend/src/components/PreferenceSettings.tsx` and `frontend/src/lib/i18n/catalog.ts` to the explicit reviewed mutation list; settings/page.tsx need not change just to reach this slot. Keep LegacyDatabaseImport SQLite-only. Export should use existing allowlisted browser snapshot/package creation plus a user-selected save operation, with cancellation/error/source-preservation behavior. Explain that this artifact carries the allowlisted browser portion, not all native files. Do not emit a supposedly importable package with a fabricated target identity while pair admission is unresolved.

6. **Recovery isolation still needs exact bootstrap/capability definitions — candidate lines 41–51.** Local Tauri 2.11.1 source indeed routes plugin calls through extend_api separately from run_invoke_handler; the existing main capability includes broad fs/store access. Native gate and a distinct capability are both needed. Freeze main-window auto-creation, minimal recovery command allowlist/sender checks, plugin initialization side effects, and the transition from first-launch choice into exclusive pending recovery before any ordinary writer starts. Existing builder plugin registration precedes setup (`lib.rs:338–361`); merely returning a different setup result does not prove those effects are absent. Source-level isolation is part of this connection task, while real installed-app proof remains separately bounded.
